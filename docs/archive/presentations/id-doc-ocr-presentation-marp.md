# id-doc-ocr 项目汇报
## 这不是一个 OCR Demo，而是证件识别平台底座原型

- 目标：讲清 **价值、现状、风险、下一步**
- 风格：**少字、强结论、能汇报**

---

# 先讲结论
## id-doc-ocr 已具备平台雏形，下一步重点是“真实可落地”

- 已有：插件化架构、规则校验、API 服务、回归测试、容器部署
- 价值：适合作为 **证件识别平台底座原型**
- 短板：前处理、真实数据、人工复核、生产化运维还需补齐
- 建议：从“架构完整”转向“真实场景能力 + 生产化硬化”

---

# 1. 为什么要做这个项目
## 通用 OCR 不等于业务可用

- 业务真正需要的不是“识别出文字”
- 而是：**稳定输出可信的结构化字段**

### 证件识别的核心要求
- 姓名 / 证件号 / 日期 / MRZ 等字段要准
- 结果要可校验、可审计、可复核
- 低置信度结果不能直接放行

<p class="small">一句话：项目要解决的是“可上线的结构化识别”，不是“看起来像对了的 OCR”。</p>

---

# 2. 项目定位
## id-doc-ocr 更像“识别系统”，不是“识别模型”

**它不是**
- 通用 OCR Demo
- 单模型试验代码
- 只看整页文本效果的工具

**它更像**
- 面向证件/票据的结构化识别系统
- 可校验、可回归、可扩展的流水线
- 未来可沉淀为统一平台底座

---

# 3. 设计原则
## 路线是对的，这很重要

- **确定性优先，生成式补充**
  - 先模板/字段/规则，再上 VLM 兜底
- **字段优先于全文**
  - 关注 exact match，而不是“看起来差不多”
- **校验是一等能力**
  - 没有业务规则的 OCR，不能直接上线
- **人工复核是系统一部分**
  - 低置信度必须能接人工

---

# 4. 系统架构
![bg right:42% contain](./id-doc-ocr-arch.png)

## 主流程
- 输入图像 / 扫描件
- 文档检测 Detector
- 透视矫正 / 质量评估 Rectify
- 文档分类 / 插件路由
- OCR 主识别 + Parser 解析
- Validator 规则校验
- 低置信度走 VLM / KIE Fallback
- 输出结构化结果或进入人工复核

## 关键信息
- 这是 **多阶段流水线**
- 不是单模型一步到位

---

# 5. 当前已经做到了什么
## 项目骨架已经比较完整

### 已支持插件
- china_id
- passport
- boarding_pass
- hukou_booklet
- train_ticket
- medical_record

### 已具备能力
- OCR / VLM 多后端适配
- API：`/health` ` /capabilities` ` /infer`
- CLI 工具链
- Docker / Compose / Makefile
- 回归测试与 JSON 报告

---

# 6. 为什么说它不是普通 Demo
## 工程化能力已经接近“平台原型”

- 有 **API 服务**：可以接系统
- 有 **CLI 工具**：可以本地跑、批量跑
- 有 **Docker / Compose**：可以部署
- 有 **回归机制**：可以持续验证质量
- 有 **插件化设计**：可以持续扩文档类型

<p class="small">这意味着它已经从“模型实验”进入“平台原型”阶段。</p>

---

# 7. 当前成熟度判断
## 架构和解析层较完整，但底层识别能力仍偏 Demo / 骨架态

### 比较成熟的部分
- 项目定位清晰
- 插件化结构完整
- parser / validator 较扎实
- API / CLI / Docker 已打通
- 文档与回归机制较完整

### 还不够成熟的部分
- detector / rectify 仍偏 mock
- GOT-OCR 仍是 placeholder
- regression 更偏 fixture / public sample
- 生产化监控、告警、审计、复核后台仍需补齐

---

# 8. 可量化现状
## 当前结果说明“规则解析层”已经比较稳定

- parser regression：**11 / 11** fixtures passed
- 预期字段匹配：**89 / 89**
- overall field exact-match rate：**1.0**

## 应该怎么解读
- 说明：已建模场景下，parser / validator 层较稳定
- 不代表：真实线上复杂拍照场景已经同样成熟

---

# 9. 主要风险
## 真正的挑战在“真实场景”和“产品化闭环”

- 真实复杂场景仍需验证
  - 模糊 / 反光 / 遮挡 / 畸变 / 多模板差异
- 当前测试结果偏理想化
- 插件扩展会带来长期维护成本
- 多模型路线会引入环境、性能、稳定性复杂度
- 人工复核闭环还未真正产品化

---

# 10. 下一步建议
## 优先级要从“继续堆功能”转向“补关键短板”

1. **补强 detector / rectify**
2. **扩充真实数据与评估集**
3. **完善 failure case 闭环**
4. **补齐生产化能力**
   - 日志 / 监控 / 指标 / 审计 / 部署规范
5. **推进人工复核流程产品化**

---

# 11. 最终结论
## 这个项目值得继续投，但方式要变

### 现在的判断
- 它已经具备成为 **证件识别平台底座** 的条件
- 但下一阶段不该只继续堆模型或堆插件

### 更关键的是
- 把前处理做强
- 把真实数据评估做实
- 把人工复核和运维能力补齐

## 一句话带走
**id-doc-ocr 的价值不在“又一个 OCR 项目”，而在“它已经长成了一个可产品化的识别平台原型”。**
